# OrbitCargo — Decisions Log

Authoritative record of resolved decisions. Supersedes the "open decision" notes elsewhere in `docs/`.

| # | Date | Decision | Choice | Rationale / impact |
|---|---|---|---|---|
| ADR-001 | 2026-10-18 | **Role set** | **DS 7-role set** + Customer: Super Admin, Operation Admin, Operation Staff, Finance Admin, Finance Staff, Customer Support, Document Officer, Report Manager, Customer. | Matches the approved admin UI (Shell nav, Users screen) exactly. Permission matrix built on these roles. |
| ADR-002 | 2026-10-18 | **Access scoping** | **Country + business year + per-employee page-level overrides.** | Full fidelity to the DS admin behaviour. Staff scoped to assigned countries (Turkey/India) and active business year; `EmployeeScope` carries per-page `accessLevel` overrides. Authorization filters every query by actor's allowed countries/years. |
| ADR-003 | 2026-10-18 | **Styling approach** | **Tailwind bridged to the DS token CSS variables.** | Tokens remain the source of truth as CSS vars (exact approved values); Tailwind `theme.extend` references the same vars. Ported components keep their look; new layout uses Tailwind utilities. Resolves ARCHITECTURE D1. |
| ADR-004 | 2026-10-18 | **Currency model** | **USD only, 2-decimal, decimal math (no JS float).** | Matches the DS (USD only). Amounts stored as Prisma `Decimal`; currency recorded explicitly to allow future expansion without silent mixing. |

| ADR-005 | 2026-10-18 | **Auth session strategy** | **Auth.js v5 (Credentials) + JWT sessions, with a per-user `sessionEpoch` re-checked server-side.** | The baseline mandates Auth.js; Auth.js Credentials only supports JWT sessions (DB sessions need an external IdP). JWT can't be revoked server-side alone, so the authorization layer loads the user on every protected access and compares `sessionEpoch`; password reset / forced logout bumps it to invalidate all tokens immediately. Argon2id for hashing. |
| ADR-006 | 2026-10-18 | **MFA scope (Phase 3)** | **Deferred (documented gap + rollout plan).** `mfaEnabled` hook exists; TOTP enrollment/verification is built in a later phase. | The baseline permits documenting the gap when MFA isn't in the implemented auth config. Keeps Phase 3 bounded to core auth + authorization. See THREAT_MODEL §residual risks. |

| ADR-007 | 2026-10-18 | **Shipment status vocabulary** | **Operational set in the DB; customer-facing labels as a presentation mapping.** | The DB uses `AT_ORIGIN_STORE/DEPARTED/IN_TRANSIT/ARRIVED/DELIVERED/ON_HOLD` (design-system operational set, drives the state machine). The readme's customer-facing words (Booked/Departed/In transit/Arrived/Delayed/Delivered) are produced by `publicStatusLabel` for public tracking only. |
| ADR-008 | 2026-10-18 | **Public tracking privacy** | **Approved subset only:** tracking number, customer-facing status, mode, origin/destination (city, country), and status-change milestone timestamps. | Excludes PII, financials, documents, internal notes, staff identities and raw internal codes. Enforced by an explicit `select` in `publicTracking.ts` and a test asserting the exact key set. |

| ADR-009 | 2026-10-18 | **Charge-line model** | **Generic categorized line items** (`category` + `description` + `quantity` × `unitPrice` → server-computed `amount`); DS-specific components (quality, brand, fatura, …) expressed as additional categorized lines, not fixed columns. | Matches the baseline ("explicit charge line items", configurable categories); extensible and avoids baking in an unapproved structure. Additive if Orbit later confirms the specific component model. Totals are always recomputed server-side from lines — the client never supplies authoritative amounts. |

| ADR-010 | 2026-10-18 | **Document storage backend** | **Private filesystem store outside the web root behind a `Storage` interface; server-mediated authorized downloads + optional short-lived HMAC-signed URLs.** | No S3/MinIO provisioned; the threat model forbids public-dir storage. The interface isolates the backend so production swaps in S3-compatible storage without touching callers. Keys are app-generated random (no user filename → no traversal); every download passes object-level authz or a signed token bound to the document id. |

| ADR-011 | 2026-10-18 | **Transfer send/receive workflow** | **A `Transfer` entity with PENDING→SENT→RECEIVED states.** Capability = `transfer:write` permission + the acting employee's `transferRole` (SEND creates/sends, RECEIVE receives); super admins bypass. Country scope enforced from the user's role scopes (from-country to send, to-country to receive). | Implements the deferred inter-country transfer flow faithfully to the design system's send/receive agent model, reusing the existing permission + scope machinery. |

| ADR-012 | 2026-10-18 | **MFA implemented** (supersedes ADR-006 deferral) | **TOTP (otplib) for privileged accounts** (super admin / *_admin), seed encrypted at rest (AES-256-GCM, key derived from AUTH_SECRET), single-use hashed recovery codes. Second factor required at login when enabled; privileged users are forced to enroll before admin access. | Closes the ADR-006 gap. Verified end-to-end: integration tests for enroll/verify/recovery + an E2E that signs in with a live TOTP code. |

| ADR-013 | 2026-10-20 | **Charge-line model** (resolves the ADR-009 open item; owner decision D1 in `DESIGN_GAP_AUDIT.md`) | **Design fields become first-class on each customer cargo line:** `measure` (kg air / CBM sea) × `rate`, `quality` × `measure`, `brandPcs` × `brandRate`, `fatura`, `delivery`, `other`, minus `discount`. Line total is recomputed on the server with `Decimal`; the browser never supplies it. Generic categorized `ChargeLineItem`s remain for extra charges. | Matches the admin LineForm, InvoicePaper and customer invoice screens. Implemented in Phase 11 as an additive migration. |
| ADR-014 | 2026-10-20 | **Customer level rule** (owner decision D2) | Per business year: air tier from total kg (≥100 → 2, ≥300 → 3, ≥1000 → 4, else 1), sea tier from total CBM (≥1 → 2, ≥4 → 3, ≥10 → 4, else 1); level = max tier → 1 D·BASIC, 2 C·STANDARD, 3 B·VIP, 4 A·PRO. Computed server-side from shipment lines; thresholds kept in one config module. | Same rule as the design's `ORBIT_RULES.levelOf`, confirmed by the owner. Implemented in Phase 11. |

| ADR-015 | 2026-10-20 | **Data storage** (owner decision on `docs/requirements/ORBIT_BUSINESS_SPEC.md`) | **PostgreSQL stays the source of truth.** The spec's "saved in the browser" is not adopted. | The browser's storage is per-device, can be cleared, and can't be authorised or audited. Money, receipts and permissions must be server-side. The spec's "survives refresh" requirement is met by the database. |
| ADR-016 | 2026-10-20 | **Login flows** (supersedes the single shared form of 2026-10-20) | **Customer:** Customer Reference + password. First login or forgotten password: Reference + Phone + Email → email OTP → create password. "Create New Account" self-registration issues a Reference shown in an in-app notification. **Staff:** 3 steps — Employee ID → email + emailed verification code (first time only) → create password / enter password. Privileged staff keep TOTP MFA (ADR-012) as an extra step. | Matches spec A1/B1. Server-side: OTPs are random, hashed, expiring, single-use and rate-limited. Identifiers are verified against the account (no enumeration). Step 3 asks for the **Orbit** password only — never the user's real Gmail password. |
| ADR-017 | 2026-10-20 | **Shipment statuses** (supersedes ADR-007's 6-status set) | **4 statuses:** AT_ORIGIN_STORE → DEPARTED → TRANSIT (Air only) → ARRIVED. `DELIVERED` and `ON_HOLD` are removed by migration (existing `DELIVERED` rows → `ARRIVED`). Status changes only in Operations, per shipment, applying to all its customers. AT_ORIGIN_STORE is set automatically. | Spec §0. The public-tracking label mapping is updated to the same four words. |
| ADR-018 | 2026-10-20 | **Customer level** (confirms ADR-014 over spec A10/B5) | **KG/CBM-based (ADR-014)**, not the spec's invoiced-value thresholds. | Owner decision. The thresholds stay in one config module, so switching later is a one-line change. |
| ADR-019 | 2026-10-24 | **Accounting Out categories** (resolves a conflict in the owner's revised admin prompt, §11) | Out has **6** categories: Shipment cost, Expenses, Commission, Transfer Money, Debt, and **Profit payout** (Turkey partners: Somali Transport, Mahad). | The prompt limits Out to 5 categories but also records partner payouts through "Out → Profit payout". Owner chose to add the sixth. Owner also re-confirmed ADR-015 (PostgreSQL) and ADR-018 (KG/CBM level) on 2026-10-24, and asked for **Phase 15 (Finance) before Phase 14**. |
| ADR-020 | 2026-10-24 | **Opening balance from earlier years** (owner request: only 2026 data goes into the system, but earlier years' balances must be recorded with their sources) | Table `OpeningEntry`: one line per country + year with *from year*, *source* (Profit, Transfer Money, Commission, Somali Transport, Mahad, Debt, Shipment cost, Other), a signed amount (+ held, − owed or lost), bank and note. Lines add to the Balance, per-bank records, partners' "what we hold" and each row of "What this balance is made of". **Debt** lines are money owed to us: not in the balance until returned, listed in Debts, repaid with an IN receipt (`DebtReturn` now points at a CashOut **or** an OpeningEntry). Only `accounting:manage` may add or reverse a line. Lines are reversed, never deleted, and are locked once January – June of that year is closed. **Closing a year** now writes next year's lines, split by source plus every debt still owed, instead of one total in `OpeningBalance`; legacy `OpeningBalance` rows still count. | **Revised the same day (owner):** an earlier year is entered as its **balance first**, then the **banks** it is in, then **what the money is** (Profit, Transfer Money, Commission, Shipment cost, Other; Somali Transport and Mahad only where the country splits profit). Both splits must equal the balance (checked on the server). Lines are `kind` TOTAL / BANK / SOURCE / DEBT. Saving a year again reverses its old lines (kept in History). Only typed banks and parts are shown. A year close carries the total, per-bank amounts (incl. "not in a bank") and parts. Lines typed in the first version were converted by migration `20261024240000_opening_years`. **Paying an earlier year later (owner):** an Out can "belong to" an earlier year that has an opening balance (`CashOut.forYear`, plus `reference`, e.g. "W-30", when the shipment is not in the system). It is checked against what that year left for the matching part (Shipment cost → Shipment cost, Transfer → Transfer, Commission → Commission, Expenses → Profit, Profit payout → the partner). It has its own receipt (note "For 2025 · W-30") and is deducted once, from this year's balance. The earlier year shows each part's paid and left amounts and the list of these payments. A shipment of a closed system year (2026 onward) can be chosen and its stage is marked paid. |
